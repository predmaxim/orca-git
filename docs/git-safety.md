# Git safety

Every git command the worker (`src/worker/`) runs, where its inputs come from, how they are checked, what happens when it fails, and which test covers it. The plugin runs git on its users' repositories: nothing it does may damage a repository or lose work. Checked against git 2.56.0 on 2026-11-10.

## Rules every call follows

- git starts only through `createGit` (`src/worker/git.ts`): `execFile`, never a shell, with `-c core.quotepath=off -c color.ui=false -c log.showSignature=false` in front, `GIT_TERMINAL_PROMPT=0` (never asks for a password) and `LC_ALL=C`, a 60 s timeout (120 s for rebase, merge, cherry-pick, revert and fetch). The only shell git itself starts is the interactive rebase's sequence editor and `exec` lines, with every word single-quoted (`shQuote`).
- A request names its repository by `root`. The worker accepts only a path that is the top level of its own repository (`gitFor` in `main.ts`).
- No value from a frame ever becomes a git option. Commit hashes must match `^[0-9a-f]{40}$`. A hash given to a command that reads a bare 40-hex argument as a branch of that name first (`git checkout --detach`, `git checkout -b`, `git branch`, the backup branch) is passed as `<hash>^{commit}`; a checkout of a commit is asked for explicitly (`detach: true`), never guessed from the text. Branch and tag names go through `assertName` (`actions.ts`): trimmed, not empty, not starting with `-`, no `@{`, not under `refs/`, not a full commit hash (40 or 64 hex digits, any case), and accepted unchanged by `git check-ref-format --branch` (tags: `git check-ref-format refs/tags/<name>`). A branch to merge or rebase onto is sent as its full ref (`refs/heads/…` or `refs/remotes/…`, never a short name, which can mean another ref: `heads/x` is branch `x`, `tags/x` tag `x`, and a tag wins over a branch of the same name); the ref must exist exactly (`git show-ref --verify --quiet <ref>`) and name a commit (`git rev-parse --verify -q --end-of-options <ref>^{commit}`). File paths come after `--` as `:(literal)<path>`.
- Actions on the current branch (cherry-pick, revert, reset, Undo Commit, the rewrites, merge and rebase onto) and those that move HEAD elsewhere (checkout, a new branch checked out) carry the HEAD the confirmation showed (`expectHead`, null for a branch with no commit yet); the worker refuses one that comes without it (`ON_HEAD` in `main.ts`), runs them only while HEAD is still there and no operation is in progress (checked before anything is made), and makes the backup the user asked for first (`runGuarded` in `backup.ts`). Undo is bound to the HEAD the action left; the panel offers it only when the worker reported that HEAD. Merge, rebase onto and a force delete also carry the commit the menu showed the branch at (`tip`) and run only while the branch still points there.
- While a rebase, merge, cherry-pick or revert is stopped (started in a terminal, say), every action that moves HEAD or touches the index or the files is refused. "Stopped" is what `git status` reports: `rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` or a `sequencer` todo list in the git dir (`operationInProgress` in `rebase.ts`). Creating a branch without checkout or a tag only adds a ref and stays allowed. When only a cherry-pick or revert todo list is left (no commit stopped on; earlier versions of the plugin could leave one), the refusal and the panel's banner say so and point to `git cherry-pick --quit` / `git revert --quit`, which keep staged changes.
- Create Patch saves only inside the repository, by the user's decision of 2026-11-10: a path outside it (`~/Downloads`, say), inside `.git` (or the git dir under any other name) or through a link is refused; the patch can be copied to the clipboard instead.
- What git prints on stderr as a line starting exactly `warning: ` or `Warning: ` (so not a hook's `WARNING:`) while a command that changes something succeeds comes back with the result: it says what was left behind (commits on no branch, a branch deleted though only its upstream holds it). A message git wraps is joined into one line: the next line counts when the previous one ends without `.`, `:`, `!` or `?` and it is indented or starts in lower case and is no `hint: ` or other `word: ` line. The line-ending conversion warnings (`LF will be replaced by CRLF`, one per file under `core.autocrlf`) become one line with their count. At most five lines and a count of the rest (`gitWarnings`; `noteWarnings` in `warnings.ts`, around `runAction`, `runBranchAction` and `fetchAll`); the banner shows them under the message and stays until closed (test "the banner gets git's own warnings, the line-ending ones as one line").
- Rewrites, merge and rebase onto run with `--autostash`. When they fail they are aborted, which re-applies the stash; when they succeed but the stash does not apply cleanly, the banner says the changes are in the stash and offers no Undo. When git re-applies the stash cleanly, after the operation or after its abort, it puts the changes back without their staging: new files stay added, and a file staged and then edited again keeps only its work-tree version. With the conflicts of a stash that does not apply, files can stay staged, and the stash entry keeps everything as it was. Whenever files staged before are no longer staged, the message says so (row 46).

Test names below are from `src/worker/safety.test.ts` unless a file is named; `git.test.ts`, `branchActions.test.ts`, `backup.test.ts`, `main.test.ts` and `selection.test.ts` sit next to it.

## Known limits

- Reset --hard discards local changes and overwrites or deletes whatever stands where the target puts its files. The stash backup keeps only changes to tracked files. Before the Reset dialog opens the worker checks the work tree (`reset.check`, rows 47–54), and the hard reset is always confirmed, also with the stash box ticked. Both dialogs list what the stash does not keep (README, "Backups before risky operations"): untracked files, ignored ones included, at a path the target has and the index or work tree lacks (or inside a folder there), files named like a folder the target needs, and the same inside a nested repository, checked on disk without following links. First and in bold come the repositories (folders holding `.git`) inside a folder the target replaces with a file, at any depth, which the reset deletes whole with their files and any history kept in them; then, in bold, any such folder the search could not finish (over 10,000 entries, or unreadable). A folder where a file marked `--assume-unchanged` is tracked gets the same search. With `submodule.recurse=true` the reset also resets submodules, so a folder where the target has one is listed like any other, and every submodule of the index or the target that is populated, or holds files of the user's, is named in bold as reset or removed; what is inside it (uncommitted changes, untracked files, commits on no branch) is not checked one by one, and neither the backup nor the stash keeps it. Edits to files marked `--assume-unchanged`, which git status and the stash skip but the reset writes back, are found by hash (row 54) and listed in bold. Not listed: a file created after the dialog opened (the worker does not check again when the reset runs).
- An index of more than roughly 550,000 entries, depending on path length (or a target tree that large, with `submodule.recurse`) passes the worker's 64 MiB output buffer: the reset check then skips files marked assume-unchanged and submodules and says so in bold, and the Reset dialog still opens. `git status` and the target diff (rows 47–48) have the same buffer, but only list changed paths.
- Reset (and restore to a backup) moves the branch away from commits a remote branch already holds without a pushed warning; the commits stay on the remote.
- Pushed means "a remote-tracking branch holds it": a push from another machine that was not fetched is not seen.
- A bisect in progress is not treated as an operation in progress.
- Leaving a detached HEAD (row 55) asks also when only the stash, a note or `refs/original/` keeps those commits, where git itself would not warn.
- The checks of HEAD (`expectHead`) and of a branch's tip (`tip`) and the action after them are separate git processes: a change a terminal makes in the milliseconds between them is not caught.
- Fetch follows each remote's configured fetch refspec: a mirror-style refspec such as `+refs/*:refs/*` (or one writing into `refs/heads/` or `refs/tags/`) still moves or replaces local branches and tags, backups included. The plugin does not check refspecs (not probed).
- Existing branches whose names start with `refs/` or are a full commit hash (40 or 64 hex digits) cannot be checked out, renamed or deleted from the panel (the name check refuses them); a terminal still can. Names such as `ORIG_HEAD` or `FETCH_HEAD` still pass the name check.
- A file staged and then edited again comes back from a rewrite, merge or rebase onto with only its work-tree version: git's autostash does not keep the staged one. The message says the staging was lost.
- A stale `MERGE_AUTOSTASH.lock` (left by a git that crashed): `git merge --quit` stores the changes in the stash list but cannot delete the ref, so the next merge refuses, and following its advice (`git merge --quit` again) would store the same changes a second time. Delete the stale lock first.
- The git dir check of the patch path (row 25) relies on the file system resolving another name for `.git` (NTFS `.git.`, `GIT~1`, `.git::$INDEX_ALLOCATION`) to the same real path; it was tested on Linux with a separate git dir inside the work tree, not on Windows. If the first check (on the nearest existing folder) misses such a name, the folders the patch needs are made before the second check refuses, so they can be left behind, empty, inside the git dir.
- The patch path is checked, then written: the file itself is opened so that it never replaces or follows a link made in between, but a folder of the path swapped for a link in between is not caught.
- A stale `.git/HEAD.lock` (left by a git that crashed): `git switch` and `git checkout` (rows 1, 2 and 2b) write the target's tree into the index and files, then fail to move HEAD, so the files are switched while HEAD is not and the message only says the checkout failed. Delete the stale lock, then run the same checkout again: it finishes the switch and keeps local changes (probed on git 2.56.0). Do not restore the files from HEAD instead: that would also discard local changes the checkout carried along.
- A stale `.git/config.lock`: Checkout as… (row 2b) creates the branch, then fails to record its tracking; the branch stays without an upstream, and only git's own message is shown. HEAD, index and files are unchanged.
