# Git safety

Every git command the worker (`src/worker/`) runs, where its inputs come from, how they are checked, what happens when it fails, and which test covers it. The plugin runs git on its users' repositories: nothing it does may damage a repository or lose work. Checked against git 2.56.0 on 2026-11-10.

## Rules every call follows

- git starts only through `createGit` (`src/worker/git.ts`): `execFile`, never a shell, with `-c core.quotepath=off -c color.ui=false -c log.showSignature=false` in front. The only shell git itself starts is the interactive rebase's sequence editor (`cp '<todo>'`) and `exec` lines (row 11): the paths in them (the git executable, the todo and message files) are single-quoted (`shQuote`), the other words are fixed, and `cp` is found through the cleaned `PATH` below.
  - Which git: an absolute path, resolved by `resolveGit` (`src/worker/launch.ts`) when the runner is made. A Git executable setting that is a full path is used as it is and must be a file that can be run; on Windows only a drive (`C:\`) or UNC (`\\server\`) path counts, and one without an extension is tried with the `.com` and `.exe` of `PATHEXT`, as Windows runs it. A bare name (the default `git`) is looked up only in the absolute folders of `PATH`: empty, `.` and other relative entries are skipped (on Windows `\tools` and `/x` too: they hang off the current drive), and on Windows each folder is tried with the `.com` and `.exe` of `PATHEXT` in its order (`execFile` starts nothing else without a shell). A relative path with a separator (`./git`, `bin\git.exe`, `C:git`, `\Git\cmd\git.exe`) is refused. Given a bare name, Windows (libuv's `search_path`) first starts a `git.exe` or `git.com` in the folder git runs in, which is the repository, and a `.` or empty `PATH` entry does the same on Linux and macOS. The rebase todo's `exec` line (row 11) runs the same absolute path.
  - Environment: the worker's own, without the variables that send git to another repository or add config to every call: each name `git rev-parse --local-env-vars` prints (row 55: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_COMMON_DIR`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT` and the rest) and every `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>`, names compared in upper case. `PATH` keeps only the entries that pass the same check as above, and is left out when none does (an empty `PATH` means the current folder): git finds what it starts by name there too, such as the rewrite's `cp`, `ssh`, `gpg` and `git-lfs`, so a `.` entry would run the repository's own. Then `GIT_TERMINAL_PROMPT=0` (never asks for a password), `LC_ALL=C` and `GIT_EDITOR=:`: git takes a message as it is and never waits for an editor. Every message the plugin writes goes in with `-m` or `-F` (rows 11 and 22; merge and revert use `--no-edit`), and the tags are lightweight (`--no-sign`, rows 4 and 21). Orca 1.4.253 starts the worker with only `PATH`, `HOME`, `USERPROFILE`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TZ`, the temp folders and a few Windows variables, so none of these come from Orca today; the cleaning does not depend on that.
  - Time limits: a subcommand the worker only reads with (`READ_ONLY` in `git.ts`: `log`, `rev-parse`, `rev-list`, `diff`, `status`, `ls-files` and the like) is killed after 60 s. `git fetch` is killed after 100 s, under the 120 s a panel waits: it only waits on the network. It runs with `-c fetch.parallel=2`, so with several remotes the per-remote fetches git starts die with it; one by one (`fetch.parallel=1`, git's default, or `0` on a single CPU, since `0` means the CPU count) the running one went on writing refs after the kill. Refs a fetch updated before the kill stay. Every other command runs to the end, because a checkout, reset, merge or rebase killed half way is left half done. If git is killed anyway (from outside, or past the 64 MiB output cap), the message ends with "git <command> was stopped before it finished. If it was changing the repository, the change may be half done: check with git status." "On failure" in the tables below is git refusing or failing, not a kill.
- A request names its repository by `root`. The worker accepts only a path that is the top level of its own repository (`gitFor` in `main.ts`); with the environment cleaned as above, every later call stays in that repository.
- One change per repository at a time: `action.run`, `branch.run`, `backup.delete` and `repo.fetch` hold a lock on their root (`exclusive` in `main.ts`) until git ends. Another one meanwhile is refused with "Another git operation is still running in this repository", never queued behind it; reads go on. A panel waits at most 120 s for a request (Orca clamps a longer `timeoutMs`). After that it says git is still running, until the change ends, instead of reporting a failure. The panel sends each of these four with a request id; the worker posts its result as `action.done` with that id, and the panel that stopped waiting for that id shows the result as it would have (Undo, the backup made, the stash hash), or at once if it came just before the panel gave up. A result for a repository other than the one shown is named ("In <name>: …") and gets no buttons. When the worker starts, it posts `worker.started`, and the panel drops every wait for the worker before it and says that how the change ended is not known.
- No value from a frame ever becomes a git option. Commit hashes must match `^[0-9a-f]{40}$`. A hash given to a command that reads a bare 40-hex argument as a branch of that name first (`git checkout --detach`, `git checkout -b`, `git branch`, the backup branch) is passed as `<hash>^{commit}`; a checkout of a commit is asked for explicitly (`detach: true`), never guessed from the text. Branch and tag names go through `assertName` (`actions.ts`): trimmed, not empty, not starting with `-`, no `@{`, not under `refs/`, not a full commit hash (40 or 64 hex digits, any case), and accepted unchanged by `git check-ref-format --branch` (tags: `git check-ref-format refs/tags/<name>`). A branch to merge or rebase onto is sent as its full ref (`refs/heads/…` or `refs/remotes/…`, never a short name, which can mean another ref: `heads/x` is branch `x`, `tags/x` tag `x`, and a tag wins over a branch of the same name); the ref must exist exactly (`git show-ref --verify --quiet <ref>`) and name a commit (`git rev-parse --verify -q --end-of-options <ref>^{commit}`). File paths come after `--` as `:(literal)<path>`.
- git output that carries text (commit messages, author and committer names, paths, config values) is read with NUL between fields (`-z`, `%x00`), never with another separator: a commit message, a path or a config value can hold every byte but NUL, and an author name control characters. The first-parent history a rewrite works on must also be one unbroken chain of distinct 40-hex commits (row 33), and the log drops a row whose hash is not 40-hex or came already (row 39). Every `log`, `show` and `format-patch` that prints commit text runs with `--encoding=UTF-8`, so `i18n.logOutputEncoding` neither garbles it nor turns it into UTF-16.
- git versions: the plugin needs git 2.31 or later: Create Patch's check of the git dirs uses `rev-parse --path-format=absolute`, which git 2.30.6 prints back as one more path, and older git was not checked. The check for an operation in progress (row 34) does not rely on it: it reads the plain `--git-path`, resolved against the root, and refuses unless git printed exactly one path, so even an unrecognized option fails closed. The worker enforces it: when `git version` (row 58) reads below 2.31, every request that changes the repository is refused before it starts, with the version found and the one needed: `action.run` and `branch.run` (so no backup is made either), `backup.delete` and `repo.fetch`. The log, details, diffs, the checks behind the dialogs, Create Patch and the Diff tab still work. A version that cannot be read refuses nothing. Options newer than that are chosen by version or avoided: `--empty=stop` from 2.45 with `--empty=ask` before (rows 10 and 58), and `-c rebase.updateRefs=false` instead of `--no-update-refs` (2.38+). Checked with the exact arguments on git 2.34.8, 2.43.7 and 2.45.4 (Alpine containers), the worker tests on 2.39.5 (Debian 12 container), and the whole suite on 2.56.0.
- Actions on the current branch (cherry-pick, revert, reset, Undo Commit, the rewrites, merge and rebase onto) and those that move HEAD elsewhere (checkout, a new branch checked out) carry the HEAD the confirmation showed (`expectHead`, null for a branch with no commit yet); the worker refuses one that comes without it (`ON_HEAD` in `main.ts`), runs them only while HEAD is still there and no operation is in progress (checked before anything is made), and makes the backup the user asked for first (`runGuarded` in `backup.ts`). Undo is bound to the HEAD the action left; the panel offers it only when the worker reported that HEAD. Merge, rebase onto and a force delete also carry the commit the menu showed the branch at (`tip`) and run only while the branch still points there.
- While a rebase, merge, cherry-pick or revert is stopped (started in a terminal, say), every action that moves HEAD or touches the index or the files is refused. "Stopped" is what `git status` reports: `rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` or a `sequencer` todo list in the git dir (`operationInProgress` in `rebase.ts`). A `rebase-merge` that holds `autostash` but no `head-name` is a rebase that never started (git before 2.47, row 12): `describeRepo` reports it as `autostashOnly`, and the panel's banner and every refusal give the steps that bring the changes back instead of "finish or abort", which fails there. Creating a branch without checkout or a tag only adds a ref and stays allowed. When only a cherry-pick or revert todo list is left (no commit stopped on; earlier versions of the plugin could leave one), the refusal and the panel's banner say so and point to `git cherry-pick --quit` / `git revert --quit`, which keep staged changes.
- Create Patch saves only inside the repository, by the user's decision of 2026-11-10: a path outside it (`~/Downloads`, say), inside `.git` (or the git dir under any other name) or through a link is refused; the patch can be copied to the clipboard instead.
- What git prints on stderr as a line starting exactly `warning: ` or `Warning: ` (so not a hook's `WARNING:`) while a command that changes something succeeds comes back with the result: it says what was left behind (commits on no branch, a branch deleted though only its upstream holds it). A message git wraps is joined into one line: the next line counts when the previous one ends without `.`, `:`, `!` or `?` and it is indented or starts in lower case and is no `hint: ` or other `word: ` line. The line-ending conversion warnings (`LF will be replaced by CRLF`, one per file under `core.autocrlf`) become one line with their count. At most five lines and a count of the rest (`gitWarnings`; `noteWarnings` in `warnings.ts`, around `runAction`, `runBranchAction` and `fetchAll`); the banner shows them under the message and stays until closed (test "the banner gets git's own warnings, the line-ending ones as one line").
- Rewrites, merge and rebase onto run with `--autostash`. When they fail they are aborted, which re-applies the stash; when they succeed but the stash does not apply cleanly, the banner says the changes are in the stash and offers no Undo. When git re-applies the stash cleanly, after the operation or after its abort, it puts the changes back without their staging: new files stay added, and a file staged and then edited again keeps only its work-tree version. With the conflicts of a stash that does not apply, files can stay staged, and the stash entry keeps everything as it was. Whenever files staged before are no longer staged, the message says so (row 46).

Test names below are from `src/worker/safety.test.ts` unless a file is named; `git.test.ts`, `branchActions.test.ts`, `backup.test.ts`, `main.test.ts` and `selection.test.ts` sit next to it.

## Known limits

- With git before 2.47 (seen on 2.34.8, 2.39.5, 2.43.7 and 2.45.4; fixed by git commit bf6ab087d1, "rebase: apply and cleanup autostash when rebase fails to start", in the 2.47.0 release notes; 2.47.3 and 2.56.0 checked; 2.46.x not checked), a `pre-rebase` hook that refuses a rewrite (row 10) or rebase onto (row 16) leaves `.git/rebase-merge` holding only git's autostash: the uncommitted changes are gone from the files and `git rebase --abort` fails ("could not read head-name"). The worker does not repair git's state itself; it detects this (row 12) and its message, the panel's banner and every refusal say to run `git rebase --quit`, which stores the changes in the stash list, then `git stash pop --index`, which brings them back with their staging (plain `git stash pop` if that reports conflicts in the index). Both steps were checked on git 2.34.8, 2.39.5 and 2.45.4: files, staging, HEAD and the stash list come back as they were. Until then every action that moves HEAD is refused.
- Reset --hard discards local changes and overwrites or deletes whatever stands where the target puts its files. The stash backup keeps only changes to tracked files. Before the Reset dialog opens the worker checks the work tree (`reset.check`, rows 47–54), and the hard reset is always confirmed, also with the stash box ticked. Both dialogs list what the stash does not keep (README, "Backups before risky operations"): untracked files, ignored ones included, at a path the target has and the index or work tree lacks (or inside a folder there), files named like a folder the target needs, and the same inside a nested repository, checked on disk without following links. First and in bold come the repositories (folders holding `.git`) inside a folder the target replaces with a file, at any depth, which the reset deletes whole with their files and any history kept in them; then, in bold, any such folder the search could not finish (over 10,000 entries, or unreadable). A folder where a file marked `--assume-unchanged` is tracked gets the same search. With `submodule.recurse=true` the reset also resets submodules, so a folder where the target has one is listed like any other, and every submodule of the index or the target that is populated, or holds files of the user's, is named in bold as reset or removed; what is inside it (uncommitted changes, untracked files, commits on no branch) is not checked one by one, and neither the backup nor the stash keeps it. Edits to files marked `--assume-unchanged`, which git status and the stash skip but the reset writes back, are found by hash (row 54) and listed in bold. Not listed: a file created after the dialog opened (the worker does not check again when the reset runs).
- An index of more than roughly 550,000 entries, depending on path length (or a target tree that large, with `submodule.recurse`) passes the worker's 64 MiB output buffer: the reset check then skips files marked assume-unchanged and submodules and says so in bold, and the Reset dialog still opens. `git status` and the target diff (rows 47–48) have the same buffer, but only list changed paths.
- Reset (and restore to a backup) moves the branch away from commits a remote branch already holds without a pushed warning; the commits stay on the remote.
- Pushed means "a remote-tracking branch holds it": a push from another machine that was not fetched is not seen.
- A bisect in progress is not treated as an operation in progress.
- Leaving a detached HEAD (row 56) asks also when only the stash, a note or `refs/original/` keeps those commits, where git itself would not warn.
- The checks of HEAD (`expectHead`) and of a branch's tip (`tip`) and the action after them are separate git processes: a change a terminal makes in the milliseconds between them is not caught.
- Fetch follows each remote's configured fetch refspec: a mirror-style refspec such as `+refs/*:refs/*` (or one writing into `refs/heads/` or `refs/tags/`) still moves or replaces local branches and tags, backups included. The plugin does not check refspecs (not probed).
- Existing branches whose names start with `refs/` or are a full commit hash (40 or 64 hex digits) cannot be checked out, renamed or deleted from the panel (the name check refuses them); a terminal still can. Names such as `ORIG_HEAD` or `FETCH_HEAD` still pass the name check.
- A file staged and then edited again comes back from a rewrite, merge or rebase onto with only its work-tree version: git's autostash does not keep the staged one. The message says the staging was lost.
- A stale `MERGE_AUTOSTASH.lock` (left by a git that crashed): `git merge --quit` stores the changes in the stash list but cannot delete the ref, so the next merge refuses, and following its advice (`git merge --quit` again) would store the same changes a second time. Delete the stale lock first.
- The git dir check of the patch path (row 25) relies on the file system resolving another name for `.git` (NTFS `.git.`, `GIT~1`, `.git::$INDEX_ALLOCATION`) to the same device and inode; it was tested on Linux with a separate git dir inside the work tree (and a folder whose name differs only in case), not on Windows. A name that `lstat` reports missing but `mkdir` finds existing is checked before anything is made inside it.
- The patch path is checked, then written: the file itself is opened so that it never replaces or follows a link made in between, but a folder of the path swapped for a link in between is not caught.
- A stale `.git/HEAD.lock` (left by a git that crashed): `git switch` and `git checkout` (rows 1, 2 and 2b) write the target's tree into the index and files, then fail to move HEAD, so the files are switched while HEAD is not and the message only says the checkout failed. Delete the stale lock, then run the same checkout again: it finishes the switch and keeps local changes (probed on git 2.56.0). Do not restore the files from HEAD instead: that would also discard local changes the checkout carried along.
- A git that never ends (a hook waiting on something, say) keeps its repository's lock: further changes to that repository are refused until the process is killed, and then the message says it may be half done.
- If the worker stops while git runs (Orca restarts it, say), the new worker no longer holds that repository's lock and does not know about that git, which may still be running; the panel says the outcome is not known.
- A stale `.git/config.lock`: Checkout as… (row 2b) creates the branch, then fails to record its tracking; the branch stays without an upstream, and only git's own message is shown. HEAD, index and files are unchanged.
