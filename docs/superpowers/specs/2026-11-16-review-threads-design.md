# Обсуждения в заметках ревью, как в Azure DevOps — дизайн

Дата: 2026-11-16. Статус: решения пользователя из разговора 2026-11-16, после живой проверки заметок. План — `docs/superpowers/plans/2026-11-16-review-threads.md`. Дополняет и местами заменяет «Этап 1» из `2026-11-15-review-notes-design.md`: всё, что здесь не названо, остаётся как там (привязка к блобу, папка отправки, защита записи, скилы ревью, markdown без `innerHTML`).

Источники, все на 2026-11-16: ветка `worktree-review-notes`; документация плагинов Orca 1.4.259 (`references/host-api.md`); бандл Orca 1.4.258.

## Зачем

После живой проверки пользователь попросил сделать заметки как обсуждения в pull request'ах Azure DevOps: заметка остаётся, агент отвечает в ней же, можно писать дальше, а закрывает её пользователь кнопкой «Решено».

## Что меняется

| Было | Стало |
|---|---|
| У заметки один текст и один ответ агента | Заметка — обсуждение: сообщения пользователя и агента по порядку |
| Правка заметки стирает ответ | Ничего не стирается само: сообщение удаляет только кнопка «Удалить» |
| На заметку — один ответ | Сообщений сколько угодно: после ответа агента пользователь пишет дальше |
| Каждый раз новый агент | Тот же агент, если его терминал открыт и он свободен; иначе новый, с историей обсуждения |
| Картинка в ответе — текст с путём | Картинки в сообщениях: миниатюра, по нажатию — просмотр во всплывающем окне, Esc закрывает |
| Состояния нет | «Активно» и «Решено» |

Не цель из прежнего дизайна «переписка в несколько раундов» снята.

## Обсуждение

- **Сообщение:** автор (пользователь или агент), текст в markdown, время, картинки. У сообщения агента — вердикт (`answered`, `confirmed`, `refuted`, `unclear`), «исправлено» и вид агента. У сообщения пользователя — отправка, с которой оно ушло.
- **Новое сообщение** пишется в поле под последним сообщением (Enter сохраняет, Shift+Enter — новая строка, Esc — отмена), как первое сообщение заметки.
- **Текст обязателен:** Enter у сообщения с картинками без текста ничего не сохраняет и пишет под полем «Напишите текст сообщения».
- **Правка:** сообщение пользователя можно менять, пока оно не отправлено. Отправленное — история, которую видел агент.
- **Удаление:** у каждого сообщения своя кнопка; удалить можно и своё, и агента. Удаление последнего сообщения удаляет обсуждение. Кнопка обсуждения удаляет его целиком. Каждое удаление обсуждения или сообщения (в карточке и в строке списка «Заметки») спрашивает ещё раз на месте, как «Удалить все» (решение T-R9, 2026-11-16): первое нажатие переводит кнопку в состояние подтверждения (красная, подпись и подсказка «Нажмите ещё раз, чтобы удалить»; в узком списке — только подсказка), второе удаляет; уход фокуса с кнопки, Esc или перерисовка возвращают её как была. Удалённый ответ агента не возвращается: сообщения пользователя той отправки остаются отправленными (их по-прежнему нельзя изменить), но больше не ждут ответа — с них снимается отправка, и папка отправки удаляется, когда её не называет ни одно сообщение, так что файл ответа уже не прочитается.
- **«Отправить снова»** у отправленных сообщений без ответа снимает с них отметку «отправлено»; ничего не удаляет.
- **«Решено»** нажимает пользователь, когда ответ устроил. Решённое обсуждение сворачивается в одну строку (её нажатие разворачивает) и агенту больше не отправляется. «Открыть снова» возвращает. Новое сообщение в решённом обсуждении открывает его.
- **Состояние обсуждения** показывает метка, в таком порядке: «Решено»; «Отправлено, ответа нет» (на последнюю отправку ответа нет — даже если уже написан новый текст); «Не отправлено» (есть неотправленные сообщения); вердикт последнего ответа агента. У обсуждения ждёт ответа не больше одной отправки: пока ждёт, новый текст не отправляется (его можно дописывать и менять), «Отправить снова» снимает ожидание.

Поля заметки: привязка как раньше (`path`, `side`, `blob`, `rev`, `start`, `end`, `quote`), `id`, `createdAt`, `messages`, `resolvedAt?`. Поля сообщения: `id`, `author`, `body`, `at`, `images?`; у пользователя `review?`, `sentAt?`; у агента `review` (на какую отправку ответ), `verdict`, `fixed`, `agent?`.

## Отправка

- Отправляются обсуждения не решённые, не ждущие ответа и с неотправленными сообщениями; остальные из выбранных пропускаются. Меню: «Все неотправленные» и «Этот файл», как раньше.
- **Кому.** Worker помнит терминал агента, которому ушла последняя отправка репозитория. Если этот терминал есть среди агентов workspace (`agents.list`) и агент свободен, промпт печатается в него (`terminal.sendText`, с Enter). «Свободен» — только состояние `done`: что покрывает `waiting`, Orca не документирует, а строка с Enter в агента, ждущего ответа, ответила бы за пользователя. Запись о терминале проверяется: тот же репозиторий, непустой `terminalId`, вид агента как в `agents.list`. Отправка без `agent` — прежнему агенту; не свободен в момент доставки — откат и «выберите агента». Отправка с `agent` всегда запускает нового агента, даже если прежний свободен. Пока прежний агент свободен, меню видов не показывается.
- `terminal.sendText` принимает только терминалы активного worktree и печатает текст как ввод: промпт остаётся одной строкой без обратных кавычек (та же проверка). Текст промпта один для запуска и для печати, и в его постоянных словах нет метасимволов оболочки; печатаемый промпт ещё и не должен их содержать (`' " $ ; & | < > ( ) \ * ? ! # ~ { } [ ]`) — принести их может только путь репозитория. Такой репозиторий в терминал не печатает никогда: `notes.agent` отвечает «нет агента», фрейм предлагает нового, а отправка без `agent` отклоняется «выберите агента», ничего не записав (решение T-R8, 2026-11-16: строка, попавшая в оболочку вместо агента, не должна ничего запустить). `agent: null` значит то же, что отсутствующий `agent`. Если печать отклонена, отправка откатывается, а пользователь видит причину; следующая попытка предложит нового агента.
- Новое право манифеста: `terminal:send`. Обновление попросит одобрение заново.
- Папка отправки та же (`review-<id>/`: `notes.md`, `SKILL.md`, `answers/`). В `notes.md` на обсуждение: привязка, затем все сообщения по порядку с автором, временем и путями картинок; сказано, что ответить надо на последние сообщения пользователя. Строка заголовка сообщения и строка `Images:` с полными путями его картинок (сразу под заголовком) стоят в колонке 0, текст сообщения — с отступом в четыре пробела, так что строка текста не выдаёт себя ни за заголовок, ни за картинки. Заголовок сообщения агента называет сообщения пользователя той отправки, на которые он ответил (`[3] agent (refuted, fixed: no), <время>, answers [1]:`; ничего, если таких сообщений не осталось): ответ на прошлую отправку, вставший после нового текста, не читается как ответ на него. В начале `notes.md` и в руководстве сказано, как показать картинку (сохранить рядом с файлом ответа и написать `![подпись](имя-файла.png)` с голым именем файла) и что файлы строки `Images:` приложены к этому сообщению и их надо открыть. Тот же агент получает ту же историю: она в файле, а не в его памяти; поэтому руководство начинается с «You are an independent reviewer», без «fresh».
- Что уходит, worker берёт из хранилища последним делом перед записью папки, после чтения скилов: сообщение, дописанное пока отправка ждала, попадает в `notes.md` и отмечается вместе с ним; написанное после записи — нет.
- Ответ — файл `answers/<id обсуждения>.md` в прежней форме (`verdict:`, `fixed:`, пустая строка, markdown). Он становится сообщением агента в обсуждении. Переписанный файл заменяет это сообщение (то же правило сравнения, что раньше); ответы прошлых отправок не трогаются. Ответ встаёт в конец обсуждения, после уже написанного нового текста. Ответ для решённого обсуждения тоже сохраняется, обсуждение остаётся решённым: ожидание ответа не зависит от «Решено». Корни, которые событие агента берёт из ключа `pending` (фреймы делят хранилище), проверяются, как корень от фрейма (`gitFor`): не корень репозитория пропускается с записью в лог, и под ним ничего не читается, не сохраняется и не удаляется.

## Картинки

- **Приложить к сообщению:** вставкой из буфера (Ctrl+V в поле сообщения; текст, вставленный вместе с картинкой, вставляется как обычно) или кнопкой «Приложить файл» с полем пути и подсказками, как у скилов ревью. Пропускает ли фрейм Orca вставку картинок — проверить вживую; поле пути работает в любом случае.
- **Формат:** PNG, JPEG, GIF, WebP (тип определяется только по первым байтам, расширение не проверяется), до 5 МиБ, до 5 картинок на сообщение.
- **Хранение:** файлы в `<корень worktree>/.orca-git-log/images/`, имя — первые 12 hex от sha256 содержимого и расширение. Так агент читает картинку по пути из `notes.md`, а повторная вставка не плодит копий. Файл удаляется, когда на него не ссылается ни одно сообщение репозитория; загрузка, так и не приложенная к сообщению, удаляется через сутки; повторно сохранённый файл с теми же байтами получает время «сейчас», так что сутки отсчитываются заново (если время поставить не удалось — на Windows для этого нужно право записи, — файл всё равно берётся).
- **Картинки агента:** в ответе `![подпись](файл)` с файлом из папки `answers/` своей отправки (подпись до 300 символов, адрес до 1024: поиск без неограниченных повторов, так что ответ из незакрытых `![a](` разбирается за миллисекунды). Worker копирует такой файл в `images/` и прикладывает к сообщению; ссылка на файл вне `answers/`, ссылка-симлинк или неподходящий файл остаётся текстом.
- **Передача.** Сообщение фрейма ограничено 64 КиБ, ответ worker'а — 1 МиБ, поэтому картинка идёт частями: от фрейма по 45 000 байт, к фрейму по 600 000. Во фрейме части собираются в `Blob`; CSP разрешает `blob:` для картинок.
- **Показ:** миниатюры под текстом сообщения. Нажатие открывает картинку во всплывающем окне поверх вкладки; Esc или нажатие мимо закрывает.

## Хранение

- Одно значение на обсуждение: ключ `note:<sha256 корня>:<id>`. Порядок и список — в `notes:<sha256 корня>` (`{ root, ids }`). Прежнее значение этого ключа со списком заметок (формат не выпускался) считается пустым.
- Список заметок (`notes.list`) отдаёт не больше 900 000 байт обсуждений (JSON каждого, в UTF-8; ответ worker'а ограничен 1 МиБ): сначала нерешённые, затем решённые, внутри — новые первыми; вошедшие идут в порядке хранения. Сколько не вошло, говорит предупреждение «N обсуждений не показано». «Удалить все» удаляет все обсуждения репозитория, и не показанные тоже (`notes.delete { all: true }`).
- Терминал последнего агента: `agent:<sha256 корня>` (`{ root, terminalId, agent }`).
- Лимиты: до 200 обсуждений на репозиторий, до 100 сообщений в обсуждении, текст пользователя 1–4000 символов, ответ агента до 8000. Лимиты Orca: значение до 262144 байт, всего 5 МиБ, до 1024 ключей. Отказ записи показывается пользователю.

## Риски

- **Печать в терминал вслепую.** Между проверкой «агент свободен» и печатью он может заняться; текст тогда встанет в его очередь ввода или потеряется. Заметка останется «отправлено, ответа нет», есть «Отправить снова».
- **Вставка из буфера** во фрейме может быть запрещена Orca: остаётся поле пути.
- **Хранилище:** 5 МиБ на весь плагин. Длинные обсуждения во многих репозиториях его заполнят; запись тогда отклоняется с сообщением.
- **Картинки — недоверенные файлы:** worker проверяет тип и размер и никогда не исполняет их; во фрейме они попадают только в `<img>` через `blob:`.
