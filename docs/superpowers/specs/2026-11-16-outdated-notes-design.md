# Заметки ревью после изменения кода: перенос и «Устарела» — дизайн

Дата: 2026-11-16. Статус: дизайн, не реализован. Решения пользователя: «1 отмена, не запрещать. 2 а. 3 нет», дизайн утверждён («1. да. 2. да»), без пометки «с коммита» у перенесённых — запрета push нет; вариант 2а — перенос заметок как в GitLab и Gerrit и метка «Устарела»; устаревшие заметки ничего не запрещают. Дополняет `2026-11-16-review-navigation-design.md`. Редакция 2 (2026-11-16): после проверки исполнителем — перенос не требует, чтобы коммит заметки был предком (squash, fixup, amend и rebase плагина ломают это), `--inter-hunk-context=0` и `--text`, старая сторона не устаревает, метка в списке — только для заметок из истории HEAD.

Источники, все на 2026-11-16: `main` на `3411dee`; git 2.56.0 (опыты во временном репозитории); документация GitHub, GitLab (и её исходники `lib/gitlab/diff/position_tracer/line_strategy.rb`, `line_mapper.rb`), Azure DevOps, Gerrit («Porting comments»), Bitbucket, Phabricator, Cursor, VS Code GitHub PR; бандл Orca 1.4.259.

## Зачем

Заметка написана на коммите A, а коммит B потом поменял файл. Если выделить A и B вместе (или смотреть более поздний коммит), заметки в диффе нет: вкладка показывает заметку, только когда blob её стороны равен blob'у этой стороны диффа (`notesOfFile`, `src/shared/notes.ts`). Пропадает она даже тогда, когда B только вставил строки выше неё (проверено в `/tmp`). Пользователь не видит ни заметки, которая всё ещё про этот код, ни того, что код под заметкой уже изменили.

## Как это у других (проверено по источникам выше)

- Комментарий на строках, которые потом не менялись, переносится в новую версию со сдвигом номеров (GitLab, Azure DevOps, Gerrit, Phabricator).
- Если строки комментария изменились или удалены, он «устарел» (Outdated): в коде его не рисуют — у чужого кода он сбил бы с толку (так же рассуждает Orca для PR-комментариев), — а показывают в списке с меткой и ссылкой на исходную версию (GitHub, GitLab, Bitbucket, VS Code, JetBrains).
- Устаревший не значит решённый: закрывают вручную. Автозакрытие есть только в GitLab, и то по отдельной настройке.

## Цели

1. В диффе, который показывает более позднюю версию файла, заметка с нетронутыми строками стоит на своих (сдвинутых) строках — как будто написана на этой версии.
2. Заметка, чьи строки потом изменились, помечена «Устарела» в списке «Заметки» вкладки и под файлом в секции «Файлы»; в коде её нет; клик открывает коммит, где она написана (как сейчас, `notes.open`).
3. Агент знает, что заметка устарела, и сверяется с текущим файлом.

## Не цели

- Запрет или предупреждение при push (пользователь отказался).
- Автоматическое «Решено» для устаревших.
- Перенос назад (заметка с более позднего коммита на более ранней версии) и перенос через переименование, случившееся до показанного диффа.
- Хранение перенесённой позиции: она считается заново при показе, хранится только исходная привязка.

## Анти-цели

- Заметка нарисована у строк, которые уже не те, что она обсуждает.
- Метка «Устарела» у заметки, чьи строки не менялись (только сдвинулись).
- Заметка исчезает из списка или меняет состояние «Решено» сама.

## Подходы

- **Перенос по диффу blob'ов — выбрано (вариант 2а).** `git diff -U0 <blob заметки> <blob стороны диффа>`: строки вне изменённых кусков сдвигаются на разницу длин кусков выше; пересечение с куском — «Устарела». Так делает GitLab (`LineMapper`), только по версиям MR. Дёшево: один процесс git на пару blob'ов, путь не нужен.
- **`git blame --reverse` — отвергнуто:** идёт по истории и дороже, а нужен только ответ «изменились ли эти строки между двумя версиями».
- **Хранить и обновлять перенесённую позицию (GitLab `position`) — отвергнуто:** версий здесь нет, дифф выбирает пользователь; пересчёт при показе проще и не устаревает сам.
- **Только метка «Устарела» без переноса (2б) — отвергнуто пользователем.**

## Правило переноса

Для заметки N (сторона s, blob `bN`, коммит `rev`, строки `[start, end]`) и стороны s показанного файла (blob `bT`, коммит `cT`: `to` для новой стороны, `from` для старой):

1. `bN === bT` — заметка своя, как сейчас.
2. Кандидат — только если путь заметки — путь этой стороны файла (новая: `path`; старая: `oldPath ?? path`), либо путь до переименования внутри показанного диффа (`oldPath`, когда заметка на новой стороне и файл переименован в этом диффе).
3. Не назад: если `cT` — предок `rev` и не равен ему (`git merge-base --is-ancestor cT rev` с кодом 0), показанная версия старше заметки — заметка в этом диффе не показывается и не помечается. Предком `rev` для `cT` быть не обязан (решение исполнителя): fixup, squash, reword, rebase и amend — в том числе действия самого плагина — переписывают коммит заметки, а именно тогда правку и проверяют; содержимое сравнивается напрямую по blob'ам, так что неродственная история не мешает. Неизвестный `rev` (код 128, удалён после сборки мусора) — то же, что «не предок».
4. `git diff -U0 --inter-hunk-context=0 --text --no-color --no-ext-diff --no-textconv bN bT` (`--inter-hunk-context=0` — иначе настройка `diff.interHunkContext` склеивает куски вместе с неизменёнными строками между ними; `--text` — иначе атрибуты `-diff`/`binary` из `.gitattributes`, которые git сверяет и с id blob'ов, дают «Binary files differ»; проверено исполнителем на git 2.56.0); заголовки кусков `@@ -a,b +c,d @@` (`b`/`d` по умолчанию 1). Кусок со `b > 0` занимает строки `a..a+b-1`; кусок с `b = 0` — вставка после строки `a`, она внутри заметки, если `start <= a < end`. Пересечение хоть с одним куском — **устарела** (только для заметок новой стороны: заметка старой стороны почти всегда стоит на строках, которые её же коммит удалил, и «устарела» бы в каждом более позднем диффе; она только переносится, когда строки целы). Иначе строки сдвигаются на сумму `(d - b)` кусков, целиком выше `start`; колонки остаются.
5. Перенесённая заметка — как своя: карточка у новых строк, подсветка, метка на карте файла, строка под файлом в «Файлах» с новыми номерами; никаких пометок о переносе (решение пользователя 2026-11-16: строки не менялись — пометка не нужна).
6. Последняя строка без перевода строки, к которой дописали строку, считается git'ом изменённой: заметка на ней получит «Устарела», хотя текст тот же. Принимается, как в GitLab.
7. Бинарный файл, ошибка git или blob, которого нет (сборка мусора), — заметка в этом диффе не показывается и не помечается; ошибка в лог worker'а.

## «Устарела» в списке и для агента

- Для списка «Заметки» (вся история репозитория) worker считает «устарела» относительно HEAD только для заметок новой стороны, чей `rev` — предок HEAD (`merge-base --is-ancestor rev HEAD`, код 0): заметка с другой ветки или переписанного коммита метки не получает (решение исполнителя: без общей истории «устарела относительно HEAD» не значит ничего, а «пути нет в HEAD» у заметки чужой ветки — не изменение кода). Для них: blob пути заметки в HEAD (`git cat-file --batch-check` одним процессом на все пути, ввод `HEAD:<path>`) равен `bN` — актуальна; пути в HEAD нет — устарела (файл удалён или переименован); иначе — правило 4 между `bN` и blob'ом HEAD. HEAD без коммитов — меток нет. Заметки старой стороны меток не получают.
- `notes.list` отдаёт это вычисленное поле (`outdated?: true`), в хранилище оно не пишется. Результаты пар blob'ов кешируются в памяти worker'а (ключ — пара blob'ов): blob неизменяем.
- Метка «Устарела» (`d-label` приглушённая, подсказка: «Код этих строк изменился после коммита <короткий rev>») — в строке списка рядом с состоянием и в подсказке строки «Файлов».
- В «Файлах» под файлом выделения устаревшая заметка (кандидат по правилу 2–4 с пересечением) стоит строкой с приглушённым пунктирным кружком и исходным номером строки; клик открывает её коммит (`notes.open`).
- `notes.md` для агента: у устаревшей (относительно HEAD) заметки строка `Outdated: the code at these lines changed after <rev>; compare with the current file before acting.` после строки `Lines:`.
- Счётчики не меняются: «Заметки (N)» — незакрытые, устаревшие тоже; «Решено» — только руками.

## Где считать

Только worker: у него git и заметки. Новый запрос `notes.place { root, files: SelectionFile[] }` → по каждому файлу — перенесённые (`{ id, start, end }`) и устаревшие (`id`) заметки-кандидаты; файлы без кандидатов не обходятся. Вкладка зовёт его для показанного файла при отрисовке (и при `notes.changed`), панель — для своих файлов выделения после их загрузки и при `notes.changed`. Сопоставление «своих» (правило 1) остаётся в `src/shared/notes.ts` без git.

## Ограничения

- Новые команды git (`merge-base --is-ancestor`, `diff -U0` двух blob'ов, `cat-file --batch-check`) — строки в `docs/git-safety.md`: входы — blob'ы и hashes из хранилища и из файлов выделения (40 hex), пути — только как `HEAD:<path>` во вводе `cat-file`, не в аргументах.
- Заметок до 200; кандидатов на файл — только с тем же путём, пар blob'ов — не больше числа заметок.
- `git diff` двух blob'ов не зависит от пути (`--text`, `--no-textconv`, `--no-ext-diff`); `diff.algorithm` пользователя действует, как и во вкладке Diff, так что куски совпадают с показанными.
- Строки интерфейса — `en` и `ru`; вид — `orca-plugin-ui`; концы строк файлов сохраняются.

## Что остаётся исполнителю

Форма ответа `notes.place`, имена, как вкладка и панель ждут ответ (без мигания карточек), формат кеша, точный вид пунктирного кружка в пределах правил.
